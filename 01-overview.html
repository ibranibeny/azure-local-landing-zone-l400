1. Azure Local overview

1. Understand Azure Local before building the lab

Azure Local brings Azure-managed infrastructure to a customer location. In the connected, hyperconverged deployment covered here, physical machines contribute Hyper-V compute and Storage Spaces Direct storage. Windows and Linux virtual machines, and Kubernetes workloads running on AKS on Azure Local, consume that infrastructure. Azure remains the management plane; this is not a copy of every Azure service running inside a rack.

This guide follows an educational Jumpstart LocalBox deployment: Azure Local machines are themselves nested virtual machines inside one Azure VM. Deployment evidence begins on 16 October 2026; the update Installed state, both nodes Up, and Ubuntu ownership on AzLHOST1 were recorded on 17 October 2026. None is a live health assertion for 18 October. Read the architecture and evidence boundaries, choose the correct deployment path in chapter 2, then work through the prerequisites and stop conditions in chapter 3.

Follow a management request through the layers

  1. Start in Azure. An administrator authenticates with Microsoft Entra ID and submits an operation through the portal, Azure CLI, PowerShell, or a Bicep/ARM deployment. Azure Resource Manager applies the resource model and Azure role-based access control.
  2. Locate the local target. Azure Arc projects the infrastructure into Azure. A custom location identifies the Azure Local deployment target; it is not a public Azure region or a geographical relocation of the hardware.
  3. Translate the operation locally. The Azure Arc resource bridge is an appliance VM hosting a Kubernetes management cluster. Its Azure Local VM operator/controller extension turns supported Azure VM lifecycle requests into local fabric operations.
  4. Run the workload. Hyper-V executes the guest on a cluster node. Storage Spaces Direct pools eligible node-local drives and provides resilient storage; Cluster Shared Volumes expose shared storage to the cluster. Virtual networking connects workload interfaces to the intended networks.
  5. Observe two different responsibilities. Azure reports resource provisioning and management status; operating-system and application checks establish whether the guest is actually healthy. Neither a green ARM deployment nor an Arc connection alone proves application availability.

1.1 Establish the CAF / Azure Landing Zones boundary

Proposed enterprise target, not deployed lab: the current Azure Landing Zones (ALZ) architecture includes Platform management-group children Security, Management, Identity, and Connectivity, each with its corresponding shared-service subscription. Under Workload Landing Zones, the Local management group contains an Azure Local Clusters subscription and an Applications subscription. Corp and Online remain other workload categories; Local is not an Azure region or a network hub. This placement allows Azure Local-specific policy without imposing unsuitable cloud-VM assumptions on hybrid infrastructure.

The actual exercise uses one disposable subscription and resource group; no enterprise hierarchy, subscription vending, central Sentinel workspace, ExpressRoute, or production landing zone is established by these chapters. Treat the two subscriptions in the target as ownership/governance boundaries, not a promise that every provider supports arbitrary cross-subscription references. Validate each resource type, custom location, region, provider registration, and supported workload-placement relationship before implementing that separation. Do not move existing bridge-dependent resources merely to match a diagram.

For the target, platform engineers own cluster machines, infrastructure extensions, bridge, custom location, and infrastructure dependencies. Application teams own their workload lifecycle and data, with delegated access to approved shared placement/network/storage resources. Arc-enabled application resources belong with the workload they support; Arc-projected identity infrastructure belongs with the identity service. This follows Microsoft's hybrid resource-placement guidance, which is marked deprecated and scheduled for removal on 30 October 2026; use the maintained ALZ and Azure Local references for future decisions.

1.2 Separate three planes before troubleshooting

Execution context, authority, and transport are separate checks
PlaneRequest and permission boundaryRequired evidence
Azure control planeAdministrator → Entra authentication → ARM over HTTPS 443; Azure RBAC and policy authorize resource operations.Correct masked tenant/subscription context, scoped role, operation ID, provisioning result.
Local management planeBridge/controller → cluster APIs; authorized AD cluster operators use approved private management paths. Guest SSH and Kubernetes authorization remain additional boundaries.Bridge and extension health, current cluster state, successful authorized guest/API access.
Workload data planeClients → application IP/port; Hyper-V workload switching and CSV/S2D storage carry application traffic and persistence.Actual DNS/routing, application response, dependency health, and recoverable data.

A management group distributes inherited controls; it does not proxy packets. Resource-group membership grants neither routing nor application access. Arc is not a VPN, and its private relay features do not connect arbitrary subnets. The loopback forwards later in the guide are explicit, authenticated client sessions, not an enterprise ingress design. Azure Local's firewall requirements explicitly exclude Arc Private Link Scopes for its infrastructure: required Arc endpoints resolve publicly, outbound allowlists are necessary, and HTTPS inspection is unsupported. Do not infer infrastructure Private Link support from another Arc product's capabilities.

1.3 Accept the design before accepting deployment evidence

  1. Inputs: classify data, identify a service owner, choose connected AD-based deployment, and record intended site, support release, access model, budget, and recovery objectives privately. Reader access is sufficient for inventory; later write operations need separately approved permissions.
  2. Design-area mapping: map tenant/billing to the disposable scope; identity to Entra versus AD versus guest/Kubernetes permissions; resource organization to Local placement; connectivity to explicit flow paths; security/governance to tested controls; management to monitoring and restore; automation to pinned, reviewed artifacts. See the eight ALZ design areas.
  3. Success gate: produce an approved boundary/owner matrix and dependency inventory, separating observed lab facts, proposed physical controls, and unverified assumptions. A diagram or green portal badge alone fails this gate.
  4. Failure and recovery: if ARM works but guest access fails, diagnose routing, relay, and guest authorization independently. If Arc is disconnected, avoid duplicate creation; preserve operation evidence and repair the documented connectivity/agent dependency. Running workloads may continue, but cloud-mediated management and monitoring are degraded.
  5. Rollback and operations: before any write, retain the previous configuration and approved reversal path. The platform owner handles infrastructure incidents; the workload owner proves application recovery; security reviews privileged changes and redacted audit evidence. Audit-first policies require resource/API compatibility testing before enforcement.

Inspect the resource model without changing anything

After signing in to the intended subscription, list resource types rather than publishing a full resource-ID dump. Expect separate machine, bridge, custom-location, and workload resources as the relevant stages complete. An early infrastructure-only deployment will not contain all of them.

$rg = Read-Host 'Enter your lab resource-group name'
az resource list --resource-group $rg `
  --query "[].{Name:name,Type:type,Region:location}" --output table

Nested is not production high availability. Both simulated nodes share one outer VM and its storage, network, and failure domain. A nested node restart can demonstrate cluster behavior, but cannot establish physical fault isolation, production throughput, recovery objectives, or hardware certification.
