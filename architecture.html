L400 architecture: Azure landing-zone alignment

An editable six-view design pack connects the governance model to actual deployment boundaries, protocols, resource ownership, application access and operational acceptance gates. Read it alongside all six revised chapters.

Download editable draw.io pack Download six-page PDF Download all six editable SVGs

Alignment is not a compliance claim. The landing-zone hierarchy is an enterprise target design. The recorded LocalBox implementation used one disposable subscription and resource group; enterprise management-group placement, centralized security services and production recovery controls were not deployed or proven by this guide. Labels explicitly distinguish target, recorded and unverified controls.

1. Translate CAF design areas into implementable boundaries

The current Azure landing-zone reference model separates the platform landing zone from workload landing zones. Its management-group hierarchy includes Local alongside Corp and Online. Local can organize Azure Local cluster resources and application subscriptions. This is governance taxonomy, not a command that automatically moves resources across subscriptions or establishes hybrid routes.

Choose resource placement with the service's supported subscription, resource-group and custom-location constraints. A diagram with separate cluster/application subscriptions does not prove that every Arc VM or AKS cross-subscription arrangement is supported. Validate the actual provider/API and identity permissions before implementing separation; retain a documented exception where the service requires co-location.

View01 — landing-zone governance target

Do not model management groups as routed network segments. Network and policy changes are related decisions but require separate implementation artifacts. The diagram's platform boxes identify accountable teams for identity, connectivity, security and management; they are not a list of newly created subscriptions.

View02 — actual Azure deployment and nested network

Browser access reaches Bastion over HTTPS; Bastion reaches the outer host over private RDP3389. Hyper-V console/PowerShell Direct then reaches a nested server. NAT supplies outbound translation for allowed dependencies; it is not an application firewall. Arc control connectivity does not make the cluster management network a VPN endpoint. A native-client or IP-based Bastion path requires the appropriate SKU, feature configuration and actual routing—not only an Arc resource ID.

Detailed addresses, outside the diagram: the recorded outer Azure NIC is172.16.1.4. Its nested management vNIC is192.168.1.20; AzLMGMT is192.168.1.11, the nested router is192.168.1.1, and DNS is192.168.1.254. These are different interfaces and routing scopes, not alternative addresses for one Azure subnet. The lab's workload VLAN110 uses10.10.0.0/24 and VLAN200 uses192.168.200.0/24. Exact Azure VNet subnet prefixes are intentionally not asserted without evidence.

View03 — runtime fabric, storage and identity

Storage Spaces Direct uses the cluster's real storage layout. A cloud witness contributes to quorum; it neither stores workload copies nor supplies a third execution node. A CSV owner is its coordinator, not necessarily the node running a VM stored on that CSV. The final Arc VM's configuration and disks remain on shared cluster storage during the supported same-cluster move.

Storage-network detail: StorageA uses10.71.1.10 on AzLHOST1 and10.71.1.11 on AzLHOST2, VLAN711. StorageB uses10.71.2.10 and10.71.2.11, VLAN712. SMB storage communication and any physical RDMA design must be validated against the actual supported hardware/network reference; nested virtual switches do not demonstrate production RDMA capability. Each recorded node was allocated96GiB. Available memory is dynamic and must be checked before placing or moving a workload.

AD DS/DNS/time services are dependencies of this AD-based lab. Entra access to the Azure resource is not a substitute for domain authorization to Failover Cluster Manager. A production design must keep management identity and recovery paths available during cluster failure, and must validate physical capacity, independent failure domains and release-supported networking. Network ATC-managed configuration must be changed through supported mechanisms, not arbitrary local VLAN or switch edits.

View04 — AKS provisioning and application access

Trace provisioning separately from runtime traffic. ARM and the local operator create workload VMs from a static logical network; successful provisioning does not imply both nodes are Ready. The application service selects Ready pod endpoints. A private ClusterIP is internal to Kubernetes. The diagnostic tunnel uses a local Arc API proxy and kubectl's authorized forwarding stream; port47031 is not the website, and port8087 is not a new public ingress.

Recorded sizing and runtime controls: the control plane used Standard_K8S3_v1 (4vCPU/6GiB), and the worker used Standard_A2_v2 (2vCPU/4GiB). The NGINX pod requested25mCPU/32Mi and was limited to250mCPU/128Mi, with readiness/liveness HTTP probes and no automatic service-account-token mount. The service's selectors must resolve to a Ready backend. These controls and the version/size discovery commands remain in chapter4; they are not compressed into tiny diagram labels.

View05 — VM migration and owner proof

A live move transfers running state between eligible healthy nodes and leaves shared disks in place. The guest's hostname/IP do not identify its physical owner. Read cluster Owner Node and correlate it with guest boot/application identities. The existing owner publisher writes a timestamped observation, which the app marks stale after15seconds. Website access uses Arc SSH to the guest identity; a private tunnel reconnect alone does not prove that the guest rebooted.

The new NGINX tutorial generates an installation/boot-time identity snapshot on guest8081. It is not silently upgraded into the recorded live telemetry application on8080. When testing NGINX, query host placement separately. Do not expose a domain administrator password or cluster control API inside a workload web application.

View06 — implementation gates and control gaps

Each stage has an entry condition, authorized change, measurable exit condition and recovery boundary. A timed-out client is not a reason to submit a duplicate deployment. A disconnected local tunnel is not a reason to reboot a cluster. A failed dependency does not authorize recreating a storage pool. Retain operation evidence privately, inspect the actual failed layer and use release-supported recovery procedures.

3. Physical-target acceptance before production

  1. Validate organization and supported scope. Confirm actual MG placement, subscription ownership, region choice, custom-location/provider relationships and operational team boundaries. The resource model must be supported, not only visually separated.
  2. Prove end-to-end access. Test Entra authorization, private administrative routing, DNS/time, local domain access, guest SSH and Kubernetes authorization independently. Do not treat success at one surface as access to all others.
  3. Prove compatibility and capacity. Check supported hardware, patch/firmware combinations, guest support, reserve capacity, workload/storage networking and maintenance behavior at representative load.
  4. Prove governance compatibility. Audit policies against the actual Azure Local, bridge, Arc and workload APIs. Do not assume all resources can use Private Link or survive blanket deny-public-access policies. Use the release's documented endpoint requirements.
  5. Prove recoverability. Define workload RPO/RTO, test application-consistent backups and restore, preserve identity access and verify operational response. Quorum, mirrored storage, live migration and backup solve different failure modes.
  6. Record evidence and unresolved gaps. Publish a design decision record and named owner for every exception. A drawing and a green provisioning state do not constitute an ALZ compliance assessment.
